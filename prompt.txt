# Task: Integrate a Small Local GLiNER Model for DOM PII Detection and Redaction

We are building a Chrome browser extension that acts as a local privacy middleware for AI browser agents.

The immediate goal is to implement a **small, fast, fully local PII detector for DOM content** using GLiNER.

Do NOT use an external API for PII detection.
Do NOT send DOM content to OpenAI, Anthropic, Google, Hugging Face Inference API, or any cloud service.
The model must run locally.

## 1. First inspect the existing project

Before modifying anything:

1. Inspect the repository structure.
2. Identify:

   * Chrome extension entry points
   * content scripts
   * background/service worker
   * privacy-core package
   * existing DOM analyzer
   * existing PII detection code
   * existing model-loading code
   * build system
   * package manager
3. Read the existing architecture and determine the correct place for the DOM PII detector.
4. Do not create a parallel architecture if an existing privacy-core/DOM pipeline already exists.
5. Reuse existing interfaces wherever possible.

Explain briefly which files will be modified and why before implementation.

# 2. Model selection

Use a **small GLiNER checkpoint suitable for local inference**.

Before downloading anything:

1. Check the official GLiNER/Hugging Face model repository.
2. Identify the smallest practical checkpoint that supports custom entity labels and local inference.
3. Prefer a model that can realistically be converted/exported to a browser-compatible runtime.
4. Record:

   * exact model name
   * model repository
   * model size
   * license
   * expected inference framework
   * whether ONNX/browser inference is supported
5. Do NOT assume that a Python-only GLiNER implementation can simply run inside a Chrome extension.

If the selected checkpoint cannot realistically run inside the browser, determine the correct local deployment approach rather than pretending it can.

# 3. Architecture requirement

Implement this pipeline:

DOM
↓

↓
Text normalization/chunking
↓
Fast deterministic PII rules
↓
GLiNER local inference
↓
Unified PII detections
↓
Privacy policy engine
↓
DOM redaction/sanitization
↓

The detector should NOT directly make the final privacy decision.

Separate:

### Detection

"What PII exists?"

from:

### Policy

"Is this PII allowed for this task?"

from:

### Redaction

"How should the DOM be modified?"

# 4. Hybrid detection

Do not use GLiNER for obvious patterns if a deterministic rule is faster.

Implement a hybrid detector.

Use regex/rules for:

* EMAIL
* PHONE
* CREDIT_CARD
* IP_ADDRESS
* URL where appropriate
* obvious ID patterns where reliable

Use GLiNER for semantic entities such as:

* NAME
* PERSON
* ADDRESS
* ORGANIZATION
* LOCATION
* PASSPORT_NUMBER where supported
* NATIONAL_ID where supported
* OTHER sensitive entities defined by our taxonomy

The exact supported labels should be verified against the selected GLiNER model.

# 6. DOM extraction

Implement a DOM extraction layer that identifies meaningful user-visible content.

Handle at minimum:

* text nodes
* input values
* textarea values
* select values
* contenteditable elements
* relevant ARIA/accessibility text
* labels associated with form fields

Avoid blindly serializing the entire DOM.

Do not send:

* scripts
* styles
* irrelevant metadata
* hidden implementation details

unless they are genuinely required by the existing agent architecture.

Preserve the relationship between detected text and its original DOM element.

Example internal representation:

```typescript
interface DOMTextNode {
  nodeId: string;
  elementPath: string;
  text: string;
  source:
    | "text"
    | "input"
    | "textarea"
    | "select"
    | "contenteditable"
    | "aria";
}
```

# 11. Redaction

Do not immediately destroy the original DOM.

Implement a sanitization layer.

For example:

Original:

```text
Name: John Smith
Email: john@example.com
Phone: +91 9876543210
```

After policy evaluation:

```text
Name: John Smith
Email: john@example.com
Phone: [REDACTED]
```

The redaction layer must preserve:

* DOM structure
* element identity
* non-sensitive text
* form semantics
* agent usability

The agent should receive the sanitized representation, not the raw sensitive value.

# 12. Policy engine

Create or integrate with the existing policy engine.

The model should NOT decide:

```text
PHONE = REDACT
```

based solely on its classification.

Instead:

```text
PII Detection
+
User Policy
+
Agent Intent/Task Context
+
Data necessity
=
Final Policy Decision
```

For the initial prototype, support policies such as:

```text
ALLOW
REDACT
ALLOW_IF_REQUIRED
ALWAYS_REDACT
```

Example:

```text
PHONE
Policy = ALLOW_IF_REQUIRED
Task = Book flight
Required = true
→ ALLOW
```

Example:

```text
PASSPORT
Policy = ALWAYS_REDACT
→ REDACT
```
