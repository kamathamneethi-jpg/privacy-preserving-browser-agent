# Implement Qwen VLM–Driven Agent Execution Architecture

## Objective

Refactor the existing Privacy-Preserving Browser Agent so that **all natural-language understanding, task decomposition, task sequencing, UI reasoning, and next-action selection are performed by the Qwen VLM agent**.

Remove the existing deterministic/local planning pipeline from the execution path.

The extension should become the agent's **working memory, privacy layer, action validator, and browser executor**, while Qwen becomes the **reasoning and planning engine**.

Do NOT create another regex-based planner, deterministic GoalPlanner, TaskPlanner, keyword parser, or hardcoded workflow engine to replace the existing planners.

---

# 1. Remove the Existing Deterministic Planning Pipeline

Find and remove/disable the execution dependency on:

* `GoalParser`
* `TaskPlanner`
* deterministic goal decomposition
* regex-based task generation
* hardcoded task sequences
* domain-specific workflow planners
* hardcoded assumptions such as:

```text
navigate → search → filter → select → submit
```

The browser workflow must NOT be predetermined by local code.

The extension must not attempt to infer:

```text
task_1
task_2
task_3
...
```

from the user's sentence.

Instead:

```text
User request
+
DOM
+
Screenshot
+
existing agent state
        ↓
      Qwen
        ↓
Task plan + current task + next action
```

Qwen is responsible for understanding the request and determining the workflow.

---

# 2. Qwen Is the Planner and UI Reasoning Agent

Qwen must receive the original user request directly.

Do not preprocess the request into a deterministic task list.

For example, if the user says:

> Open Amazon, search for 1TB SSD and add WD Black into the cart.

Qwen should receive the original request:

```text
USER GOAL:
Open Amazon, search for 1TB SSD and add WD Black into the cart.
```

along with:

```text
CURRENT DOM
CURRENT SCREENSHOT
AGENT STATE
RECENT ACTION HISTORY
```

Qwen should independently determine:

1. What the user wants.
2. What the overall task should be.
3. What subtasks are required.
4. Which task should currently be performed.
5. What browser action should be performed next.
6. Whether the current task has completed.
7. Whether the plan needs to be modified because the webpage differs from expectations.

---

# 3. Extension Agent State

Create a persistent state object owned by the extension.

The extension is the source of truth for execution state.

Use a structure similar to:

```javascript
{
  sessionId: "...",

  goal: {
    userRequest: "Open Amazon, search for 1TB SSD and add WD Black into the cart.",
    status: "in_progress"
  },

  tasks: [
    {
      id: "task_1",
      description: "Open Amazon",
      status: "completed"
    },
    {
      id: "task_2",
      description: "Search for 1TB SSD",
      status: "in_progress"
    },
    {
      id: "task_3",
      description: "Find the WD Black 1TB SSD",
      status: "pending"
    },
    {
      id: "task_4",
      description: "Add the selected WD Black 1TB SSD to the cart",
      status: "pending"
    }
  ],

  currentTaskId: "task_2",

  completedTasks: [
    "task_1"
  ],

  pendingTasks: [
    "task_3",
    "task_4"
  ],

  actionHistory: [],

  lastAction: null,

  status: "running",

  iteration: 0
}
```

Do not hardcode the tasks.

The tasks above are only an example.

Qwen must generate them dynamically.

# 4. Initial Agent Invocation

When the user submits a request:

1. Store the raw user request locally.
2. Capture the current browser DOM.
3. Capture the current screenshot.
4. Run the existing privacy/redaction pipeline.
5. Construct the Qwen request.
6. Send the original user request + sanitized DOM + redacted screenshot + initial agent state to Qwen.

Initial state can be:

```javascript
{
  goal: {
    userRequest: "...",
    status: "in_progress"
  },

  tasks: [],

  currentTaskId: null,

  completedTasks: [],

  pendingTasks: [],

  actionHistory: [],

  lastAction: null,

  status: "planning",
  iteration: 0
}
```

Qwen is then responsible for creating the initial plan.

---

# 5. Qwen Input Contract

Every Qwen execution request should contain the following conceptual information:

```text
SYSTEM INSTRUCTIONS

CURRENT AGENT STATE

TASK PLAN

CURRENT TASK

COMPLETED TASKS

PENDING TASKS

RECENT ACTION HISTORY

CURRENT PAGE URL

CURRENT PAGE TITLE

SANITIZED DOM

REDACTED SCREENSHOT
```

Do not send unnecessary raw browser information.

The privacy layer must run before transmission.

# 7. Qwen Output Contract

Require strict JSON output.

Use a schema similar to:

```json
{
  "goal": {
    "description": "string",
    "status": "in_progress | completed | blocked"
  },

  "tasks": [
    {
      "id": "task_1",
      "description": "string",
      "status": "pending | in_progress | completed | blocked"
    }
  ],

  "currentTaskId": "task_1",

  "taskUpdate": {
    "completedTaskIds": [],
    "newTaskIds": []
  },

  "action": {
    "type": "CLICK | TYPE | SELECT | SCROLL | PRESS_KEY | NAVIGATE | WAIT | BACK | HOVER | DONE",
    "target": "element ID or null",
    "value": "string or null",
    "direction": "up | down | left | right | null",
    "amount": "number or null"
  },

  "replan": false,

  "reason": "short explanation"
}
```

Do not allow free-form browser instructions to be executed directly.

---

# 8. Important: Qwen Generates the Plan, But Execution Is Iterative

Do NOT execute the entire task list at once.

If Qwen returns:

```text
task_1
task_2
task_3
task_4
```

only execute the action associated with the current task.

For example:

```text
Qwen:
Task 1 = Open Amazon
Current task = task_1
Action = NAVIGATE
```

Execute only:

```text
NAVIGATE
```

Then stop and observe the browser again.

---

# 9. Observation → Reasoning → Action Loop

Implement the core execution loop:

```text
OBSERVE
   ↓
BUILD CONTEXT
   ↓
SEND TO QWEN
   ↓
RECEIVE PLAN + ACTION
   ↓
VALIDATE ACTION
   ↓
EXECUTE ACTION
   ↓
WAIT FOR PAGE STABILITY
   ↓
CAPTURE NEW DOM
   ↓
CAPTURE NEW SCREENSHOT
   ↓
UPDATE AGENT STATE
   ↓
SEND NEW STATE TO QWEN
   ↓
REPEAT
```

Never assume that the webpage behaved as expected.

The new browser state must determine what happens next.

---

# 10. Dynamic Task Completion

Qwen should determine when a task is completed based on the new DOM and screenshot.

For example:

Initial:

```text
CURRENT TASK:
Search for 1TB SSD
```

Qwen performs:

```text
TYPE "1TB SSD"
PRESS ENTER
```

After the page changes, the extension captures the new state.

Qwen sees:

```text
Search results for 1TB SSD
```

It can return:

```json
{
  "currentTaskId": "task_2",
  "taskUpdate": {
    "completedTaskIds": ["task_2"]
  },
  "action": {
    "type": "CLICK",
    "target": "el_42"
  }
}
```

The extension updates the state.

---

# 11. Allow Dynamic Replanning

The task list must NOT be immutable.

Websites are unpredictable.

Qwen should be able to return:

```json
{
  "replan": true,
  "reason": "A login dialog is blocking the intended workflow.",
  "tasks": [
    {
      "id": "task_1",
      "description": "Close the login dialog",
      "status": "in_progress"
    },
    {
      "id": "task_2",
      "description": "Continue searching for the requested product",
      "status": "pending"
    }
  ]
}
```

The extension should replace/update its task state accordingly.

Do not implement a local hardcoded rule such as:

```javascript
if (loginPopup) {
    closePopup();
}
```

Qwen should reason about unexpected UI states.

---

# 12. DOM + Screenshot Must Be Sent Together

For every meaningful observation, provide both:

```text
SANITIZED DOM
+
REDACTED SCREENSHOT
```

The DOM provides:

* element IDs
* roles
* labels
* text
* input information
* accessibility information
* interactability

The screenshot provides:

* visual layout
* visual hierarchy
* actual rendered state
* buttons/icons
* cards
* popups
* elements that may be poorly represented by HTML

Qwen should use both sources when deciding actions.

---

# 13. Screenshot Must Be Re-captured After Page Changes

After each meaningful browser action:

```text
execute action
      ↓
wait for DOM/page stability
      ↓
capture screenshot
      ↓
capture DOM
      ↓
apply privacy redaction
      ↓
send to Qwen
```

Do not reuse stale screenshots.

---

# 14. DOM Changes

Use the existing DOM observation mechanisms where possible.

Use:

* `MutationObserver`
* URL changes
* navigation events
* DOM hash/signature
* loading-state detection
* configurable stabilization delay

to determine when the page has changed.

Avoid continuously sending requests while the DOM is rapidly mutating.

Debounce observation and wait for a stable state.

---

# 15. Action Validator

Qwen must NEVER directly execute browser APIs.

Architecture:

```text
Qwen
 ↓
Structured Action
 ↓
Action Validator
 ↓
Browser Executor
```

The validator should verify:

### CLICK

* target exists
* target is currently interactable
* target belongs to the current DOM snapshot
* element ID is valid

### TYPE

* target exists
* target is an input/contenteditable/selectable field
* value is allowed by the privacy policy
* sensitive values are resolved locally when necessary

### SELECT

* target exists
* target supports selection

### NAVIGATE

* URL is valid
* navigation is permitted

### SCROLL

* direction and amount are within safe bounds

Reject invalid actions.

Never blindly execute arbitrary JavaScript generated by Qwen.

---

# 16. Preserve the Existing Privacy Architecture

Do not remove the working redaction pipeline.

The pipeline must remain:

```text
Browser DOM
     ↓
DOM PII detection
     ↓
Policy Engine
     ↓
Sanitized DOM
```

and:

```text
Browser Screenshot
     ↓
Local OCR / PII detection
     ↓
Redaction
     ↓
Redacted Screenshot
```

Only the sanitized/redacted representations should be provided to remote Qwen.

---

# 17. Sensitive User Input

Do not expose sensitive values unnecessarily to Qwen.

For example, if the user says:

```text
Change my email to alex@gmail.com
```

the agent can reason about:

```text
EMAIL_VALUE
```

while the actual value remains in the local token/secret vault when the privacy policy requires it.

The browser executor can resolve the protected value locally.

Conceptually:

```text
Qwen:
TYPE el_14 <EMAIL_VALUE>

       ↓

Action Validator

       ↓

Local Token Vault

       ↓

alex@gmail.com

       ↓

Browser
```

Do not send raw secrets to Qwen unless the active privacy policy explicitly permits it.

---

# 18. Action History

Maintain a bounded action history.

Example:

```javascript
[
  {
    iteration: 1,
    action: "NAVIGATE",
    target: "amazon.in",
    result: "success"
  },
  {
    iteration: 2,
    action: "TYPE",
    target: "el_12",
    value: "1TB SSD",
    result: "success"
  }
]
```

Use the recent history when constructing the Qwen context.

Do not send an unlimited conversation/history log.

Keep enough history for Qwen to understand:

* what was attempted
* whether it succeeded
* what changed
* whether an action is repeating

---

# 19. Prevent Infinite Loops

Implement local safety mechanisms.

Track:

```text
iteration count
same action repeated
same DOM state repeated
same screenshot state repeated
same task repeated
```

If Qwen performs the same action repeatedly without state change:

```text
CLICK el_42
CLICK el_42
CLICK el_42
```

stop automatic execution and ask Qwen to reconsider with a failure signal:

```text
The previous action produced no meaningful state change.
Re-evaluate the current UI and choose a different action.
```

Also enforce a configurable maximum iteration count.

---

# 20. Goal Completion

Qwen must explicitly indicate completion.

Example:

```json
{
  "goal": {
    "description": "Add WD Black 1TB SSD to the Amazon cart",
    "status": "completed"
  },

  "currentTaskId": "task_4",

  "action": {
    "type": "DONE"
  }
}
```

The extension should then:

```text
status = completed
stop agent loop
```

Do not assume that the goal is complete merely because the final predefined task was reached.

The final browser state should support Qwen's completion decision.

---

# 21. Agent State Should Be the Working Memory

The extension should maintain:

```text
┌──────────────────────────────┐
│       AGENT STATE            │
├──────────────────────────────┤
│ User Goal                    │
│ Overall Task List             │
│ Current Task                 │
│ Completed Tasks              │
│ Pending Tasks                │
│ Recent Actions               │
│ Current URL                  │
│ Current iteration            │
│ Agent status                 │
└──────────────────────────────┘
```

Qwen does NOT need persistent internal memory.

Each request gives Qwen the state necessary to reason about the current step.

This makes the system robust even if every Qwen API request is stateless.

---

# 22. Context Construction

Create one centralized function:

```javascript
buildAgentContext()
```

It should construct:

```javascript
{
  userGoal,
  agentState,
  currentTask,
  completedTasks,
  pendingTasks,
  recentActions,
  currentUrl,
  pageTitle,
  sanitizedDom,
  redactedScreenshot
}
```

Every Qwen invocation should use this function.

Do not construct different incomplete contexts in different parts of the extension.

---

# 23. Recommended Agent Loop API

Create a central function conceptually similar to:

```javascript
async function runAgentIteration() {
    const state = await getAgentState();

    const dom = await captureSanitizedDOM();
    const screenshot = await captureRedactedScreenshot();

    const context = buildAgentContext({
        state,
        dom,
        screenshot
    });

    const result = await callQwen(context);

    const validatedAction = validateAgentResult(result, state, dom);

    if (!validatedAction.valid) {
        return handleInvalidAction(validatedAction);
    }

    updateAgentStateFromQwen(result);

    if (result.goal.status === "completed") {
        return finishAgent();
    }

    await executeBrowserAction(validatedAction.action);

    await waitForPageStability();

    return runAgentIteration();
}
```

Adapt this to the existing architecture rather than blindly copying it.

---

# 24. Do Not Put Browser Logic Into Qwen

Qwen should return abstract actions:

```text
CLICK
TYPE
SELECT
SCROLL
NAVIGATE
WAIT
BACK
DONE
```

The extension maps those actions to actual Chrome APIs.

For example:

```text
Qwen:
CLICK el_42

       ↓

Extension:
document element registry

       ↓

actual DOM element

       ↓

element.click()
```

Qwen should never return:

```javascript
document.querySelector(...).click()
```

or arbitrary JavaScript.

---

# 25. Task IDs

Task IDs must be generated and maintained consistently.

The model can propose:

```text
task_1
task_2
task_3
```

but the extension should validate the structure before committing it.

When replanning:

* preserve completed tasks where appropriate
* preserve the original goal
* update pending/current tasks
* prevent accidental loss of execution history

---

# 26. Do Not Assume Fixed Task Types

Do not implement:

```javascript
TASK_TYPES = [
    "navigate",
    "search",
    "filter",
    "fill_form",
    "submit"
];
```

as a required planning framework.

Qwen should be able to create arbitrary task descriptions.

For example:

```text
Dismiss cookie consent
Open product comparison
Expand technical specifications
Check compatibility
Return to results
Select the second matching product
```

The extension only needs to understand the final browser action.

---

# 27. Qwen Should Reason From the Actual UI

Do not instruct Qwen:

```text
If ecommerce → search → filter → select
```

Instead instruct:

```text
Determine what action is appropriate from the
actual DOM and screenshot.

Do not assume a website's layout.

Do not assume that an expected element exists.

If the expected element is absent, inspect the current UI
and choose an alternative action or replan.
```

This is critical for generalized browser automation.

# 30. Final Architecture

The target architecture is:

```text
                     USER
                      │
                      ▼
             Original user request
                      │
                      ▼
        ┌──────────────────────────┐
        │       EXTENSION          │
        │                          │
        │ Agent State / Memory     │
        │                          │
        │ Goal                     │
        │ Tasks                    │
        │ Current Task             │
        │ Completed Tasks          │
        │ Pending Tasks            │
        │ Action History           │
        └────────────┬─────────────┘
                     │
                     ▼
          Capture current browser state
                     │
              ┌──────┴──────┐
              ▼             ▼
             DOM      Screenshot
              │             │
              ▼             ▼
        DOM Sanitizer   PII Redactor
              │             │
              └──────┬──────┘
                     ▼
                QWEN VLM
                     │
        ┌────────────┼─────────────┐
        │            │             │
        ▼            ▼             ▼
     Goal         Task Plan    Next Action
   reasoning     generation    selection
                     │
                     ▼
              Extension State
                     │
                     ▼
              Action Validator
                     │
                     ▼
              Browser Executor
                     │
                     ▼
                 Browser
                     │
                     ▼
              Page State Change
                     │
                     ▼
            DOM + Screenshot
                     │
                     └──────────────► QWEN
```

## Core principle

**Qwen owns intelligence.**

**The extension owns state, privacy, validation, and execution.**

Do not add another deterministic planner between the user and Qwen.

The extension should not decide:

> "This sentence means navigate → search → filter → select."

Instead, it should say:

> "Here is exactly what the user asked, here is the current sanitized browser state, and here is what happened on previous iterations. Qwen, decide what the goal requires and what action should happen next."

This should be the new execution architecture.
