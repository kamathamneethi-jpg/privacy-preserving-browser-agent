Task: Integrate a Free Vision/Agent Model into the Chrome Extension

We need to connect our Chrome extension Browser Agent to a free LLM provider for agent reasoning.

Model

Use:

Gemma 4 26B A4B — free

Prefer OpenRouter as the provider because it gives us access to the free model through a standard OpenAI-compatible API.

Do not hardcode the API key anywhere in the repository.

Use an environment/config mechanism appropriate for the existing extension architecture.

⸻

First: Understand the Existing Project

Before modifying anything:

1. Inspect the repository structure.
2. Read:
    * memory.md
    * progress.md
    * to-do.md
3. Identify:
    * Chrome extension entry points
    * background/service worker
    * content scripts
    * existing Browser Agent implementation
    * existing privacy-core integration
    * existing DOM analyzer
    * screenshot pipeline
    * existing model/provider abstractions
    * existing tool/action execution system
4. Do not duplicate functionality that already exists.
5. Follow the existing architecture and coding conventions.

Do not start implementing until you understand where the LLM should sit in the current architecture.

⸻

The model must sit behind the local privacy boundary.

The architecture should be:

                     USER
                       │
                       ▼
                User Instruction
                       │
                       ▼
              ┌─────────────────┐
              │ Browser Agent   │
              └────────┬────────┘
                       │
              ┌────────┴─────────┐
              │                  │
              ▼                  ▼
           DOM Data          Screenshot
              │                  │
              ▼                  ▼
        DOM Analyzer        Local Vision
              │                  │
              └────────┬─────────┘
                       ▼
                Privacy Core
        ┌──────────────┼──────────────┐
        │              │              │
        ▼              ▼              ▼
    PII Detection   Policy Engine   Privacy Vault
        │              │
        └───────┬──────┘

The cloud model must never receive raw private information that the local privacy layer has classified as protected.

⸻

Model Responsibilities

Gemma should handle:

* natural-language instruction understanding
* browser task planning
* reasoning about sanitized DOM state
* reasoning about sanitized screenshots
* selecting browser tools
* producing structured action requests

Gemma must NOT be the final authority for whether an action is allowed.

The local privacy/policy layer remains authoritative.

⸻

Browser Tools

Inspect the existing action system first.

If a tool abstraction already exists, use it.

Otherwise, create a minimal structured tool interface similar to:

click(element_id)
type(element_id, text)
scroll(direction)
navigate(url)
read(element_id)
press_key(key)
ask_user(question)

Do NOT expose arbitrary JavaScript execution or unrestricted Chrome APIs to the model.

The model should only be able to request predefined browser actions.

⸻

Structured Model Output

The model should return structured output rather than free-form text.

Example:

{
  "action": "click",
  "element_id": "checkout_button",
  "reason": "The user requested checkout."
}

For typing:

{
  "action": "type",
  "element_id": "email_field",
  "text": "<SANITIZED_EMAIL>",
  "reason": "The form requires an email address."
}

For asking the user:

{
  "action": "ask_user",
  "question": "The website requires additional information that I cannot safely infer."
}

Define a strict schema and validate model output before executing anything.

Invalid model output must never reach the browser action executor.

⸻

Privacy Boundary

This is a core requirement.

Before sending context to OpenRouter:

1. Collect DOM/screenshot information.
2. Run it through the existing local privacy-core pipeline.
3. Detect sensitive information.
4. Apply the existing privacy policy.
5. Replace protected information with safe placeholders/tokens where appropriate.
6. Build the sanitized context.
7. Only send the sanitized context to Gemma.

Example:

Raw:

Name: Shahrukh
Email: example@gmail.com
Phone: +91XXXXXXXXXX
Order: #123456

Model-visible context should look more like:

Name: <PERSON_1>
Email: <EMAIL_1>
Phone: <PHONE_1>
Order: <ORDER_ID_1>

Use the existing privacy vault/token mapping if one already exists.

Do NOT implement a second independent privacy system.

⸻

Screenshot Handling

Inspect the existing screenshot pipeline.

If the existing system can sanitize screenshots locally, use that pipeline.

Do not automatically upload raw screenshots containing private information to OpenRouter.

If screenshot sanitization is not yet implemented, clearly isolate that limitation instead of silently bypassing the privacy boundary.

The model integration must not weaken the project’s privacy guarantees.

⸻

API Layer

Create a clean model-provider abstraction.

For example:

ModelProvider
    └── OpenRouterProvider
            └── Gemma 4 26B A4B

Do not scatter OpenRouter-specific API calls throughout the extension.

The Browser Agent should interact with an abstraction such as:

generateAgentResponse(context)

rather than directly calling fetch() to OpenRouter from multiple places.

⸻

API Key Security

Do not:

* commit API keys
* hardcode API keys
* place secrets in Git
* expose secrets in source control
* print API keys to logs

Check the existing project’s configuration strategy before deciding how credentials should be supplied.

Also explain the security implications of putting an OpenRouter key directly into a client-side Chrome extension.

If the current architecture necessarily exposes the key to the extension, document this clearly rather than pretending the key is secure.

⸻

Error Handling

Handle:

* API timeout
* network failure
* rate limits
* provider errors
* invalid model output
* malformed JSON
* missing model response
* context too large
* unavailable model
* authentication failure

The extension must fail safely.

If the model fails, it should NOT automatically execute an uncertain action.

⸻

Logging

Do not log:

* raw PII
* API keys
* private page content
* unsanitized screenshots
* sensitive model prompts

Logs should contain safe debugging information such as:

Agent request created
Sanitized context generated
Model request sent
Model response received
Action proposed: click
Policy decision: ALLOW
Action executed

⸻

Configuration

Add configuration for:

provider = openrouter
model = google/gemma-4-26b-a4b

Use the exact model identifier returned by the provider/API rather than assuming the identifier.

Before implementation, verify the currently available OpenRouter model identifier and API requirements.

Do not silently substitute another model.

⸻

Testing

Add tests for at least:

1. Normal task

"Open the shopping website and search for laptops."

Expected:

instruction
→ sanitized context
→ model
→ structured action
→ policy check
→ browser action

2. PII

Give the agent a page containing:

email
phone

Verify that protected information does not enter the model request in raw form.

3. Invalid model output

Return malformed JSON.

Expected:

NO browser action

4. Policy denial

Have the model request an action that the local policy engine rejects.

Expected:

model → action
       ↓
policy → DENY
       ↓
browser action NOT executed

5. API failure

Simulate an OpenRouter failure.

Expected:

safe failure
no unauthorized browser action

⸻

Important Architectural Constraint

Do NOT implement:

Website
   ↓
Raw DOM + Raw Screenshot
   ↓
Cloud LLM
   ↓
Chrome API

That defeats the main privacy architecture of this project.

The required architecture is:

Website
   ↓
Local Perception
   ↓
Local Privacy Core
   ↓
Sanitized Context
   ↓
LLM
   ↓
Structured Action
   ↓
Local Policy Check
   ↓
Browser Action
