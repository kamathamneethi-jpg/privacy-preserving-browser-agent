Modify the existing browser agent so that it operates as a **goal-driven, multi-step browser agent** instead of converting the user's entire request into a single search query.

The system must work for arbitrary browser tasks, not just shopping.

## Core requirement

A complex user request must be decomposed into smaller executable tasks.

The agent must repeatedly:

USER GOAL
→ GOAL DECOMPOSITION
→ TASK PLAN
→ EXECUTE ONE TASK
→ CAPTURE NEW DOM
→ CAPTURE NEW SCREENSHOT
→ SEND DOM + SCREENSHOT + TASK STATE TO AI AGENT
→ AI DECIDES NEXT ACTION
→ EXECUTE
→ OBSERVE AGAIN
→ REPLAN IF NECESSARY
→ GOAL CHECK
→ CONTINUE UNTIL GOAL IS SATISFIED

Do NOT implement this as a fixed sequence.

The agent must dynamically determine the next task based on the current browser state.

---

# 1. Goal Understanding

When the user provides a request, first convert it into a structured goal.

Example:

"Find me a white Nike shoe under ₹7,000 and compare a few options"

should become something conceptually similar to:

{
"goal": "Find and compare suitable Nike shoes",
"constraints": [
{
"attribute": "brand",
"operator": "equals",
"value": "Nike"
},
{
"attribute": "color",
"operator": "equals",
"value": "white"
},
{
"attribute": "price",
"operator": "less_than_or_equal",
"value": 7000,
"currency": "INR"
}
],
"required_operations": [
"search",
"inspect",
"filter",
"compare"
]
}

However, this is ONLY an example.

The same architecture must work for requests such as:

* Find a product and compare options.
* Search for information across multiple websites.
* Fill out a form.
* Book something.
* Navigate a website and retrieve information.
* Find an item, inspect its details, and perform an action.
* Read a dashboard and summarize specific information.
* Complete a multi-page workflow.
* Find information hidden behind menus, tabs, pagination, or dynamically loaded content.

Do not hardcode domain-specific task types.

---

# 2. Task Decomposition

The planner must convert the high-level goal into smaller tasks.

Example:

GOAL:
Find a suitable product satisfying several constraints.

TASKS:

1. Identify where to search.
2. Open/search the relevant website.
3. Inspect the current page.
4. Extract candidate information.
5. Apply constraints.
6. Inspect additional candidates if required.
7. Compare valid candidates.
8. Determine whether the goal has been satisfied.
9. Perform any final requested action.
10. Return the result.

Another request may produce a completely different task sequence.

Therefore:

DO NOT hardcode:

task1 → task2 → task3 → task4

Instead implement:

goal
→ planner
→ current task
→ observation
→ next task
→ observation
→ next task
→ ...

The planner must be able to add, remove, reorder, or repeat tasks based on what happens in the browser.

---

# 3. Browser Observation MUST Happen After Every Meaningful State Change

This is critical.

After every browser action that can change the page state, capture:

1. Current DOM
2. Current screenshot
3. Current URL
4. Current browser state
5. Current task
6. Previous action
7. Relevant execution history

Examples of state-changing actions:

* navigation
* clicking
* typing
* submitting
* scrolling
* opening a dropdown
* opening a modal
* switching tabs
* changing filters
* pagination
* expanding an element
* selecting an option
* loading dynamic content

After such an action:

ACTION
↓
WAIT FOR PAGE STATE TO STABILIZE
↓
CAPTURE DOM
↓
CAPTURE SCREENSHOT
↓
SEND BOTH TO AI AGENT
↓
DECIDE NEXT ACTION

Do not allow the agent to continue blindly after an action.

---

# 4. DOM + Screenshot Must Be Sent Together

The AI agent must receive both representations of the browser state.

Conceptually:

{
"task": "...",
"url": "...",
"previousAction": "...",
"dom": "...",
"screenshot": "<image>",
"history": "...",
"goal": "...",
"constraints": "..."
}

The DOM provides:

* semantic information
* text
* attributes
* links
* buttons
* inputs
* element relationships
* accessibility information

The screenshot provides:

* visual layout
* visual hierarchy
* elements missing from useful DOM extraction
* rendered text
* images
* icons
* popups
* overlays
* visual state
* whether an element is actually visible
* spatial relationships
* page structure

The AI must use BOTH.

Do not convert the screenshot into a textual description before sending it if the selected model supports native image input.

Send the actual screenshot as an image input to the multimodal model.

---

# 5. Vision Model

Use a multimodal vision-language model as the browser-state reasoning model.

Use:

Qwen3-VL

or another currently available vision-language model with native image input.

For the prototype, configure a vision-capable Qwen model as the agent's vision/reasoning model.

The model must be capable of receiving:

TEXT + IMAGE

in the same inference request.

Do NOT use a text-only model and pretend that it has seen the screenshot.

If the primary reasoning model is text-only, implement a dedicated vision model path.

The vision model should analyze the screenshot and return structured observations/action decisions.

Qwen's tooling supports multimodal image input and explicitly exposes vision-capable model configuration, so the implementation should use the model's native image-input capability rather than OCR-only conversion.

---

# 6. AI Agent Output

Do not allow the model to return arbitrary prose as the browser action.

Require structured output.

Example:

{
"observation": {
"page_type": "search_results",
"visible_elements": [
"search box",
"product cards",
"pagination"
]
},

"goal_progress": {
"completed": false,
"reason": "More candidates need to be inspected"
},

"next_task": {
"type": "inspect_products",
"description": "Inspect visible product cards"
},

"action": {
"type": "click",
"target": "product_card_3"
}
}

The exact schema can be adapted to the existing browser-action system.

---

# 7. Action Selection

The AI should choose from the browser agent's existing supported actions.

Examples:

* navigate
* click
* type
* select
* scroll
* hover
* press_key
* go_back
* open_tab
* close_tab
* wait
* extract
* finish

The AI should NOT invent unsupported actions.

Every action must reference a valid DOM element or a valid visual target.

For DOM-based actions, prefer stable element identifiers generated by the DOM analyzer.

For visually identified elements that cannot be reliably mapped through the DOM, use the screenshot coordinates or the existing visual-action mechanism.

---

# 8. Screenshot Should Be Used for Decision Making

The current problem is:

SCREENSHOT
↓
captured
↓
ignored by agent

Fix this.

The screenshot must be included in the model request whenever a new browser state is observed.

The model should explicitly reason from the screenshot for:

* visual-only elements
* layout
* visibility
* overlays
* modal dialogs
* images
* icons
* visual product properties
* buttons whose semantic DOM information is insufficient
* page structure
* state that is apparent visually but not represented cleanly in extracted DOM

Do not rely exclusively on DOM text.

---

# 9. Dynamic Replanning

The planner must not assume that the original plan remains valid.

Example:

PLAN:
Search → inspect → filter → compare

But after searching:

OBSERVATION:
The website requires selecting a category first.

The agent should modify the plan:

Search
→ select category
→ apply filters
→ inspect results
→ compare

Another example:

OBSERVATION:
No results satisfy the constraints.

The agent should determine the next valid strategy according to the user's goal rather than simply stopping.

Possible next tasks could include:

* inspect more pages
* change search query
* try another website
* remove a non-required constraint
* ask the user for clarification if necessary

The agent must NEVER silently relax an explicit user constraint.

---

# 10. State Machine

Maintain explicit execution state.

Example:

{
"goal": {},
"constraints": [],
"plan": [],
"currentTask": {},
"completedTasks": [],
"observations": [],
"browserState": {},
"domSnapshot": {},
"screenshot": {},
"candidateData": [],
"actionHistory": [],
"failedActions": [],
"replanRequired": false,
"goalCompleted": false
}

Every browser action updates this state.

---

# 11. Goal Completion

Do not consider the task complete merely because:

* a search was performed
* a page was opened
* results appeared
* one action succeeded

The agent must evaluate whether the ORIGINAL USER GOAL has actually been satisfied.

Implement a goal checker:

CURRENT STATE
+
USER GOAL
+
CONSTRAINTS
↓
GOAL SATISFIED?

YES → finish

NO → generate next task

The goal checker should explicitly identify unmet requirements.

Example:

{
"completed": false,
"missingRequirements": [
"Need to inspect additional candidates",
"Need to verify price constraint"
]
}

---

# 12. Prevent Infinite Loops

Implement safeguards.

Track:

* repeated actions
* repeated URLs
* repeated screenshots/page states
* repeated failed actions
* number of attempts per task
* number of replans

If the agent repeatedly performs the same unsuccessful action, force replanning.

If the goal cannot be completed with available information, stop and explain what is missing instead of looping indefinitely.

---

# 14. Important Performance Rule

Do not unnecessarily send enormous DOM snapshots and full-resolution screenshots on every request.

Create an observation pipeline that:

- extracts relevant DOM information
- removes irrelevant nodes
- preserves element identifiers
- captures the current viewport screenshot
- optionally captures additional screenshots only when needed
- maintains a compact execution history

However, correctness is more important than premature optimization for the prototype.

---

# 15. Privacy Integration

This browser agent already contains a privacy boundary.

Do NOT bypass it.

The DOM and screenshot must pass through the existing privacy pipeline before being sent to any external model.

The flow should therefore be:

BROWSER
↓
DOM + SCREENSHOT
↓
LOCAL PRIVACY / PII DETECTION
↓
REDACTION / POLICY ENGINE
↓
SANITIZED DOM + SANITIZED SCREENSHOT
↓
VISION LANGUAGE MODEL
↓
ACTION DECISION
↓
ACTION VALIDATOR
↓
BROWSER

The model must never receive information that the existing privacy policy says should be blocked.

---

# 16. Implementation Constraints

Reuse the existing:

- DOM analyzer
- screenshot capture
- privacy policy engine
- PII detector
- redaction pipeline
- browser action executor
- action validator
- local privacy vault
- existing model/API infrastructure

Do not create parallel implementations of these systems.

The main change should be the introduction/improvement of:

1. Goal Parser
2. Task Planner
3. Observation Manager
4. Multimodal Vision Agent
5. Dynamic Replanner
6. Goal Completion Checker
7. Execution State Manager

---

# 17. Acceptance Criteria

The implementation is complete only when all of these are true:

### Multi-step execution

A complex user request results in multiple browser actions rather than one search query.

### Task decomposition

The high-level request is converted into smaller tasks dynamically.

### DOM observation

After meaningful browser state changes, the latest DOM is captured.

### Screenshot observation

After meaningful browser state changes, the latest screenshot is captured.

### Vision usage

The screenshot is actually passed to a multimodal model and influences the agent's decision.

### Combined reasoning

The model receives both DOM information and visual information.

### Dynamic planning

The next task depends on the current browser state.

### Replanning

Unexpected page states cause the agent to modify its plan.

### Goal validation

The agent does not stop simply because a browser action succeeded.

### Privacy

DOM and screenshot data pass through the existing privacy boundary before external model inference.

### Generalization

The implementation must work for arbitrary multi-step browser tasks and must NOT contain logic specifically hardcoded for Nike, shoes, ₹7,000, shopping, or any other single example.

Use the Nike example only as a test case demonstrating the generalized architecture.

### One important correction to your architecture

Don't do:

```text
DOM changed
    ↓
send DOM + screenshot
    ↓
LLM
```

for **literally every tiny DOM mutation**.

Modern sites can cause dozens/hundreds of DOM mutations from one action. That will destroy latency and API cost.

Do:

```text
Browser action
      ↓
wait for meaningful state stabilization
      ↓
capture DOM + viewport screenshot
      ↓
privacy pipeline
      ↓
VLM
      ↓
next action
```

So your trigger should be **“meaningful browser state change after an agent action”**, not a raw `MutationObserver` event.

For the vision model specifically, Qwen's current documentation supports multimodal image input and configurable vision models, including a dedicated `visionModel` path.

The architecture you actually want is therefore:

```text
                  USER GOAL
                      │
                      ▼
              ┌──────────────┐
              │ Goal Parser  │
              └──────┬───────┘
                     ▼
              ┌──────────────┐
              │ Task Planner │
              └──────┬───────┘
                     ▼
              ┌──────────────┐
              │Task Executor │
              └──────┬───────┘
                     ▼
                BROWSER ACTION
                     │
                     ▼
             PAGE STATE CHANGES
                     │
             ┌───────┴────────┐
             ▼                ▼
          DOM CAPTURE    SCREENSHOT
             │                │
             └───────┬────────┘
                     ▼
             PRIVACY PIPELINE
                     │
                     ▼
              ┌──────────────┐
              │ Qwen3-VL /   │
              │ Vision Agent │
              └──────┬───────┘
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
     OBSERVATION            NEXT ACTION
          │                     │
          └──────────┬──────────┘
                     ▼
                GOAL CHECK
                     │
              ┌──────┴──────┐
              │             │
             NO            YES
              │             │
              ▼             ▼
           REPLAN         FINISH
              │
              └──────→ EXECUTE
```

That is the generalized **agent loop** you're looking for, rather than a specialized “shopping planner.”
